The 180° frame flip: why base calibration had to be rewritten

Resolved & FK-verified to 1 mm / 1°

The robot and the software describe "forward" as opposite directions. Two vendors, two conventions, 180° apart. If that flip isn't accounted for, every recorded reach comes out mirrored on the real robot. Here is what the flip is, the exact numbers behind the fix, and how to reproduce it.

In one paragraph

Universal Robots' controller measures poses in its own "Base" frame; this pipeline's math (IK, MuJoCo, transforms) uses the ROS base_link frame. The two are rotated 180° about the vertical axis — so +X in one is −X in the other. The base_position/base_orientation in config.json were calibrated from a pendant reading without fully applying this flip, so the recorded motion direction was wrong. They were re-derived by rotating a pendant Tool-Position reading 180°, removing the handheld-rig offsets, and verifying against the known home pose.

01Two frames, pointing opposite ways

A "coordinate frame" is just an agreed set of directions for X, Y, Z. The problem is that the robot and the software don't agree:

+Y → left of that

base_link frame

What the IK, MuJoCo & transforms use (ROS)

+X → opposite way
+Y → opposite way

A 180° turn about the vertical axis negates X and Y and leaves Z alone. In matrix form that is the constant used throughout the code as _RZ180:

# _RZ180 : rotate 180° about vertical (Z) [ -1 0 0 ] so a point (x, y, z) [ 0 -1 0 ] → becomes (-x, -y, z) [ 0 0 1 ]

This is a standard, documented UR-vs-ROS difference — not a defect. It only bites when a number measured in one frame is used as if it were in the other.

02What went wrong when the flip was ignored

Before — flip not applied

  • Old base_orientation.yaw was -1.4° — essentially no reframe.
  • Recorded "reach forward / left" mapped to the robot's backward / right.
  • Pick-and-place came out mirrored — the wrong direction entirely.

After — flip applied

  • New base_orientation.yaw is -86.7° — the frame is properly turned.
  • Recorded directions map to the matching robot directions.
  • Pick-and-place reaches where the demonstration did.

03The calculation, with your real pendant reading

The calibration started from an actual teach-pendant Tool Position readout (the TCP pose, in UR's Base frame):

# Pendant Tool Position (UR Base frame) X = 148.82 mm Y = -708.89 mm Z = 239.41 mm RX = 1.570 rad RY = 0.044 rad RZ = -0.083 rad (≈ 90° tool tilt) # Apply _RZ180 to the position: (x, y, z) → (-x, -y, z) x: 0.1488 → -0.1488 y: -0.7089 → +0.7089 # and config stores +0.7087 ✓ matches to 0.2 mm z: 0.2394 → +0.2394

That Y value is the proof: it flips from -0.7089 to +0.7089, and the config stores +0.7087 — a match to two-tenths of a millimetre. The 180° flip is unmistakably present.

04Why config isn't just the flipped reading

X and Z do not match a bare 180° rotation — and that is expected. The pendant reports the TCP (gripper tip), but base_position needs the handheld-rig offsets removed along the tool axes. Those offsets (offset.x = 0.146, offset.z = 0.159 m) account for the ~0.17–0.18 m gaps:

So the stored calibration is flip + rig-offset removal, not the flip alone. The orientation was then not simply copied either — it was tuned and checked by running forward kinematics on the known home joint pose and confirming it reproduced to within 1 mm and 1°. That FK check is a stronger guarantee than converting a single pose.

05The neat consequence: joints line up with the pendant

There are actually two 180° hops in the chain — UR Base → base_link (in the calibration) and then base_link → the IK's internal DH frame (the runtime _RZ180). Two 180° turns cancel, so the IK's math frame lands back on UR's native Base frame. That is why the joint angles the IK produces match what the pendant reads:

Base joint — pendant 93.71° vs. IK 92.5°: about 1° apart, not 180°. If the flip had been mishandled, the base joint would have been half a turn off. It wasn't — confirming the frames are now consistent end-to-end.

06Two separate problems, two separate layers

This report and its companion cover different bugs that are easy to confuse:

This report — the 180° flip

  • A Cartesian / direction problem.
  • Decides where in space the robot reaches.
  • Wrong → mirrored pick-and-place.
  • Fixed in config.json calibration.

Companion — the wrist wrap

  • A joint revolution problem.
  • Decides which way a joint winds to get there.
  • Wrong → a joint unwinds 360° into the table.
  • Fixed with --start-joints-deg alignment.

07Re-calibrating for a new setup

  1. Read the pendant Tool Position at a known reference pose (X/Y/Z in mm, RX/RY/RZ in rad), in the Base feature frame.
  2. Apply the 180° flip — negate X and Y, keep Z — to move it into base_link frame.
  3. Remove the rig offsets (offset.x, offset.z, flange_to_tcp) along the tool axes to get the base reference, not the TCP.
  4. Verify with forward kinematics: run FK on the known home joints and confirm it reproduces the pendant pose to ≈1 mm / 1° before trusting it.
The one-line lesson. A pose is only meaningful together with the frame it's measured in. UR's Base frame and ROS base_link are 180° apart — always reframe pendant readings before feeding them to base_link-based math, then FK-verify.
